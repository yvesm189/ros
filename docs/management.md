# Managing a fleet

The console is a web application that holds three things: the devices that have
enrolled, the policy groups they belong to, and a log of what happened.

## Running it

```bash
make console            # Docker, on :8000
make console-dev        # virtualenv, auto-reload, for working on the UI
```

| Variable | Default | What it does |
|---|---|---|
| `ROS_ADMIN_PASSWORD` | `ros-admin` | The console login. Change it. |
| `ROS_ENROLLMENT_KEY` | generated | Fixes the enrollment key instead of generating one |
| `ROS_DB_PATH` | `./ros.db` | Where the SQLite file lives |

For anything beyond a lab, terminate TLS in front of it. The agent sends its
bearer token on every request and the console does not speak HTTPS itself.

```nginx
server {
    listen 443 ssl;
    server_name ros.example.org;
    ssl_certificate     /etc/ssl/ros.crt;
    ssl_certificate_key /etc/ssl/ros.key;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

## Enrolling a machine

Enrollment trades a shared key for a per-device token. The key is used once per
machine; after that the device authenticates with its own token, and rotating
the key does not disturb devices that already enrolled.

**By hand:**

```bash
sudo ros-agent enroll --server https://ros.example.org --key <key>
sudo ros-agent sync
```

**At first boot**, by shipping the server in the image. Put it in
`packages/ros-agent/etc/ros/agent.conf` before building:

```ini
[server]
url = https://ros.example.org
enrollment_key = <key>
```

The timer fires two minutes after boot, the agent finds a server and no
identity, and enrolls itself.

A machine re-imaged from the same ISO enrolls as a *new* device, because
`/etc/machine-id` is regenerated on first boot. Re-running `enroll --force` on
the same installation keeps the device record, its group and its history, and
only issues a new token.

## Policy groups

A group is a desktop configuration plus the machines assigned to it. Every
machine that is not assigned to one gets **Default**.

Saving a group publishes a new **revision**. Devices compare revisions on each
heartbeat and only fetch when theirs is behind, so a fleet of a thousand
machines that are all up to date costs one small request each per quarter hour.

The editor covers:

| Section | Settings |
|---|---|
| Appearance | colour scheme, accent, interface font, wallpapers, clock, battery percentage |
| Dock and shell | dock position, size, auto-hide, pinned applications, enabled extensions |
| Session | screen lock, blank-screen delay |
| Applications | which catalogue applications machines in the group install |
| Advanced | locked keys, and raw dconf for anything the form does not cover |

Below the form, the console prints **the exact file the agent will write**. That
preview is generated by the same code path the agent uses, and a test asserts
the two render identically — so what you read there is what lands on disk.

### Applications

Tick the applications a group should have. Machines install what they are
missing on their next sync, and the group page prints exactly what they will
act on.

Removing a tick does **not** uninstall anything. It means new machines will not
get it. Taking software off a machine somebody is using is a separate decision
and a destructive one; a sync timer is the wrong thing to be making it.

The catalogue itself is edited under **Applications**. See
[applications.md](applications.md).

### Raw dconf

The **Extra dconf** field takes JSON of `{"section": {"key": "GVariant"}}` and
overrides the form:

```json
{
  "org/gnome/desktop/wm/preferences": {
    "button-layout": "'appmenu:minimize,maximize,close'"
  },
  "org/gnome/mutter": {
    "edge-tiling": "true"
  }
}
```

Values are GVariant text, so strings carry their own quotes. Malformed JSON is
ignored rather than raising — a policy that reaches every workstation in the
fleet is not the place for a stack trace — so check the preview after saving.

### Locks

Keys listed in **Locked keys** cannot be changed by the person using the
machine. Lock sparingly; see [branding.md](branding.md#locks).

## Watching the fleet

**Devices** lists hostname, assigned policy, revision state, OS, agent version,
address and last contact. The revision column is the one that matters:

| Badge | Meaning |
|---|---|
| `r3` in blue | The device has the current revision |
| `r2 → r3` in amber | Behind; it will catch up on its next sync |
| `failed` in red | The agent could not apply the policy. The device page has the error. |

A device page also carries its hardware inventory — CPU, memory, disk, kernel,
architecture — collected on every heartbeat.

**Activity** is the audit trail: enrollments, policy saves, applications,
failures, rejected enrollment attempts and failed console logins.

## Operating the agent

```bash
ros-agent status           # what this machine thinks it is, as JSON
ros-agent sync             # heartbeat, fetch, apply
ros-agent sync --force     # apply even if the revision has not changed
ros-agent apply            # re-apply the cached policy with no network
journalctl -u ros-agent    # what the timer has been doing
systemctl list-timers ros-agent.timer
```

Local state lives in `/var/lib/ros-agent`: `identity.json` (device ID and
token, mode `0600`) and `policy.json` (the last policy applied).

To unmanage a machine, clear `url` in `/etc/ros/agent.conf` and delete
`/var/lib/ros-agent/identity.json`. The settings the console last pushed stay in
place until you also remove `/etc/dconf/db/ros.d/50-managed` and run
`dconf update`. Purging `ros-agent` does both.

## Backup

Everything the console knows is in one SQLite file.

```bash
docker compose -f management/docker-compose.yml exec console \
    python -c "import sqlite3; sqlite3.connect('/data/ros.db').backup(sqlite3.connect('/data/backup.db'))"
```

Losing it means devices keep their current policy and keep heartbeating, but
the console no longer recognises them; they re-enroll with the key and come
back as new records.
